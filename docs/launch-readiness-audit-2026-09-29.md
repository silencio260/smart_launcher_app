**Launch readiness audit — Simple Phone Launcher — 29 September 2026**

**Verdict: do not launch the reviewed version publicly.** The launcher has substantial functionality, but its advertised privacy features have reachable bypasses and inconsistent protection. Startup and encrypted storage also have failure paths that can make the entire launcher unavailable. Resolve the high-priority findings before release qualification.

This is an Android source/configuration review of the current working tree, including the pre-existing uncommitted changes. Version: 1.0.1+2. It is not certification of a built release. No application source was changed, no tests were executed, no build was produced, and no device was used. This report is the only repository file added by the audit.

**Evidence and coverage**

Reviewed startup and kit integration, onboarding/default-home handling, workspace persistence, app discovery/search/library, hiding/locking/vault flows, native file import/export and security, alarm scheduling and recovery, permissions, ads, analytics/replay, feedback, remote configuration, release signing configuration, and online wallpaper/privacy endpoints. Inspected selected shared-kit implementations where the app depends on their behavior.

Ran `flutter analyze --no-pub lib test`: **25 issues: 3 errors, 1 warning, 21 informational diagnostics**. All three errors are in the existing onboarding test; no analyzer errors were reported in app `lib`. The warning is an unused optional parameter; most informational diagnostics concern deprecated Flutter APIs. This does not validate Kotlin, manifest merging for release, R8, or SDK behavior.

An initial repository-wide analysis returned 6,111 diagnostics because it also traversed templates and nested package/example source. Those are not 6,111 launcher defects; the scoped result above is the relevant app result.

**High-priority findings**

1. **Device authentication succeeds without authentication on an unsecured phone.** [SecurityChannel.kt](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/src/main/kotlin/com/smartphonelauncherapp/smart/phone/device/launcher/smart_launcher_app/channels/SecurityChannel.kt:62>) returns success when the keyguard is absent or no device credential is configured. Vault, App Hider and App Locker lock screens treat that result as an unlock. Their fingerprint preferences can be enabled without validating enrollment. Trigger: configure a feature PIN, enable fingerprint/device unlock on an unsecured device, then use that unlock button. The feature PIN is bypassed. Fail closed when no authenticator is available, validate enrollment when enabling the option, and retain the feature PIN fallback. Evidence includes [VaultLockScreen](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/vault/presentation/screens/vault_lock_screen.dart:204>) and [VaultSettingsScreen](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/vault/presentation/screens/vault_settings_screen.dart:91>).

2. **App Hider does not protect all paths to hidden apps.** [App Library](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/app_library/presentation/screens/app_library_page.dart:95>) adds hidden apps to an ordinary Hidden folder. Its search function searches all apps without applying the hidden set, and folder opening has no authentication. Separately, [Drawer Settings](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/settings/presentation/screens/drawer_settings_screen.dart:30>) opens [Hidden Apps](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/settings/presentation/screens/hidden_apps_screen.dart:35>), where users can reveal/unhide apps without the App Hider passcode. This directly contradicts the onboarding promise to reveal only after unlock. Apply the same access rules to library browsing, search, settings, and every reveal route.

3. **The File Locker claims encryption but stores original bytes.** [Feature description](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/core/models/launcher_feature.dart:134>) describes an encrypted vault. [FileLockerStore](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/src/main/kotlin/com/smartphonelauncherapp/smart/phone/device/launcher/smart_launcher_app/channels/FileLockerStore.kt:29>) explicitly implements unencrypted copies in app-private storage, including plaintext thumbnails and native metadata. Android's app sandbox still provides protection from ordinary other apps; this finding is not a claim that all apps can read these files. However, the app does not provide the advertised file encryption. Either implement encryption with a documented recovery design or consistently describe this as private local storage and remove encryption claims from app/store materials. Confirm the intended product choice before changing storage format.

4. **Sensitive-storage key fallback is unstable and restore recovery is undefined.** [FeatureHiveStore](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/core/storage/feature_hive_store.dart:81>) catches every native key retrieval error and silently selects or creates a separate key in SharedPreferences. If encrypted boxes already use the native key, that fallback cannot decrypt them. Conversely, boxes first created with the fallback will be opened with the native key when native access later succeeds. Initialization of all sensitive boxes is required before Home mounts. This can prevent the whole launcher from starting, not just the vault. Persist a stable key mode, never silently substitute a key for existing data, and provide explicit recovery that preserves data.

   Backup compounds the issue. The app source declares no owned backup/extraction rules. The existing debug merged manifest has `allowBackup=true`, contributed by an ad dependency. The wrapped key is stored in backed-up preferences but depends on a device Keystore key. A restored install cannot be assumed to decrypt it. Define backup and device-transfer behavior for encrypted boxes, wrapped keys, raw vault files, and metadata; verify the final release manifest. Android documents the broad [default backup scope](https://developer.android.com/identity/data/autobackup). This restore failure is a source-derived risk, not a device-reproduced result.

5. **Remote configuration can restart session replay inside private screens.** [AppRuntime](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/bootstrap/app_runtime.dart:681>) pauses the recorder directly on private entry. But the shared remote-policy binder independently invokes `SessionReplayController.applyPolicy`, whose enforcement starts recording whenever rollout permits it. It does not know about `_privateScreens`; the app's plan listener only notifies listeners. A config activation while a private route is open can therefore undo the stop. Gate every recorder start through the private-screen state, including remote updates and lifecycle resumes. Bundled text/image masking is enabled, which reduces exposure, but does not satisfy the promise that these routes are never recorded. References: [policy binder](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/packages/genrevibes_starter_kit/modules/remote_config/genrevibes_remote_policy/lib/src/session_replay_remote_policy_binder.dart:110>) and [recording enforcement](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/packages/genrevibes_starter_kit/modules/analytics/genrevibes_analytics/lib/src/session_replay/session_replay_controller.dart:358>).

6. **Optional replay initialization can block the launcher.** [AppRuntime.initialize](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/bootstrap/app_runtime.dart:544>) awaits `_startReplay` before startup completes. That method awaits the replay SDK setup without a timeout and throws on a failed result. [main.dart](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/main.dart:119>) then keeps Home behind startup/retry. The configured release has a Mixpanel token and the bundled replay rollout is enabled at 100%, so this path is relevant to production. Move optional replay setup after usable Home, bound it, and degrade to a functioning launcher on failure.

7. **The public privacy disclosure does not match the implemented data flows.** The [published privacy policy](https://sites.google.com/view/simple-launcher-privacy-policy/home) was reachable with HTTP 200. It says external reporting is aggregated and anonymized, whereas runtime analytics/crash/replay explicitly use a persistent installation ID and record events per installation. It does not specifically describe session replay or Yodo1 MAS mediation, and lists products whose presence is not established by the app's active runtime. [Bundled configuration](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/config/remote_config.json:106>) enables replay for 100% of eligible release installs, with text/image masking enabled. Reconcile the policy, Play Data safety form, actual SDK collection, retention/deletion process, and any necessary regional disclosures. This is an identified disclosure mismatch; the audit does not purport to decide every jurisdiction's consent requirements.

8. **Exact-alarm eligibility is a Play release risk requiring resolution.** [AndroidManifest.xml](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/src/main/AndroidManifest.xml:52>) declares `USE_EXACT_ALARM` and limits the user-granted `SCHEDULE_EXACT_ALARM` alternative to API 32. Google's [current permission policy](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en) restricts the automatic permission to qualifying core alarm/calendar functionality. This product is a launcher with an additional clock feature, so eligibility must not be inferred merely from having an alarm screen. Unless its core-use eligibility is established, use the user-granted exact-alarm path on newer Android versions too. Also verify the full-screen-intent and special-use foreground-service declarations. Existing code does check full-screen access and offers settings recovery; absence of those checks is not a finding. [Play declaration requirements](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en) still need confirmation in Console. Rejection is a risk, not an observed decision.

**Other defects and hardening work**

- **After Call is not correctly permissioned.** [AfterCallReceiver](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/src/main/kotlin/com/smartphonelauncherapp/smart/phone/device/launcher/smart_launcher_app/receivers/AfterCallReceiver.kt:10>) assumes call-state broadcasts need no phone permission. Android's [TelephonyManager documentation](https://developer.android.com/reference/android/telephony/TelephonyManager#ACTION_PHONE_STATE_CHANGED) explicitly requires `READ_PHONE_STATE` for this broadcast. The app neither declares nor requests it, and the existing debug merged manifest does not supply it. The visible feature can be enabled yet cannot rely on receiving real call events. Remove/disable the feature or implement and disclose an appropriate permission flow. A synthetic overlay preview would not validate real call detection.

- **Legacy encrypted vault files are intentionally unreadable.** [FileLockerStore](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/src/main/kotlin/com/smartphonelauncherapp/smart/phone/device/launcher/smart_launcher_app/channels/FileLockerStore.kt:44>) rejects items without the current `raw1` marker for view/export. If any distributed build used the old AES format, upgrading strands those files. Determine whether users have that format; if so, migration/export compatibility is a release blocker. Do not erase legacy data as a recovery shortcut.

- **Private screens remain unlocked while their route survives.** [FileLockerScreen](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/lib/features/file_locker/presentation/screens/file_locker_screen.dart:57>) deliberately keeps the current unlock on resume. App Hider similarly has no background relock. The grace preference is checked on new route construction, not continuously. Switching away, locking the phone, and returning to the still-mounted route can leave content visible. Establish a background/screen-lock rule and distinguish trusted picker/auth transitions. The vault also lacks the `FLAG_SECURE` protection found on the native app-lock overlay; review screenshots and Recents previews.

- **PIN guessing is not throttled.** The vault accepts a four-digit PIN and immediately permits another attempt after failure. The credential implementation uses salted SHA-256, not a deliberately expensive password derivation function. Add persisted attempt backoff, and evaluate credential storage together with backup behavior. Preserve a safe recovery path.

- **Large vault imports can exhaust memory.** Native imports stream the initial copy, but fallback image preview generation calls `source.readBytes()` without a file-size ceiling before downsampling. A large input can exhaust the process; `catch (Exception)` does not handle `OutOfMemoryError`. Use bounded or file-backed decoding and handle low-storage/import failures without endangering originals.

- **Onboarding regression tests are stale.** [onboarding_refresh_test.dart](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/test/onboarding_refresh_test.dart:36>) references two removed strings and a removed `finish` method (lines 36, 46 and 159). Repair the existing tests to exercise the new flow. They were analyzed, not run.

- **Release signing should fail closed.** A populated local signing configuration and referenced keystore exist. However, [release build configuration](</Users/faruqshabi/AndroidStudioProjects/GENREVIBES TECHNOLOGIES INC/Launchers/smart_launcher_app/android/app/build.gradle.kts:62>) silently falls back to debug signing if the configuration is missing. Require the intended signing identity for distributable releases. Keystore existence does not verify its password, certificate match, or Play upload eligibility.

**Release evidence still required from the developer**

The source review cannot substitute for the actual release qualification. After fixing the findings, verify:

1. A signed, minified release with the production environment, correct version code/certificate, final merged permissions, and successful [16 KB native-library compatibility](https://developer.android.com/guide/practices/page-sizes) checks across bundled mediation SDKs.
2. Fresh install, existing-user upgrade, offline cold start, process recreation, default-home grant/decline/revocation, and layout/widget persistence. Include a slow or failed analytics/replay service.
3. Private-feature behavior across every entry point, lockscreen/background/Recents, unavailable biometrics, permission revocation, backup/device transfer and any legacy vault format.
4. Alarm/timer behavior under Doze, reboot, time/timezone changes, notifications denied and full-screen access denied.
5. Ad consent accept/decline/re-entry, failed loads, rapid navigation and return-to-Home; confirm no late fullscreen ad covers the launcher or another app.
6. Representative low-memory devices, Android 12–16 and major OEM variants, large app libraries, font scaling/TalkBack, widgets and gesture navigation.
7. Play Console Data safety, ads/age/content declarations, exact alarm/full-screen/foreground-service eligibility, real store screenshots and current crash/ANR/pre-launch results.
